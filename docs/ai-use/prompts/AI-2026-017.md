## Exact human-authored prompt

Implement a reproducible Rust systems-library baseline scanner in this repository.

Goal
----
Add a tool that measures how established Rust systems libraries structure safe vs unsafe code so we can compare RustyCpp migration results against real Rust systems software.

This is measurement infrastructure only. Do not draw research conclusions or choose a RustyCpp safe-percentage threshold.

Repository
----------
Current repo: ~/projects/rusty-eval

Preserve the existing src-layout and CLI style.

Create a new package/module under something like:

src/rust_baseline/
    __init__.py
    cli.py
    models.py
    scanner.py
    cargo.py
    source_scan.py
    report.py

Use the existing project conventions where appropriate rather than forcing this exact layout.

Initial crate set
-----------------
Support a manifest/config containing pinned crates/repositories.

Start with:

- redb
- rkyv
- crossbeam-epoch
- tokio
- mio
- quinn-proto
- rustix
- rustls
- blake3

The tool must NOT silently analyze whatever happens to be latest.

Each experiment must record:
- repository/crate name
- source URL
- pinned git commit or exact crate version
- scan date
- enabled Cargo features
- whether default or all-features configuration was used
- Rust toolchain version
- scanner/tool versions

Primary measurement scope
-------------------------
Measure production Rust source only.

Exclude by default:
- tests
- benches
- examples
- fuzz targets
- target/
- vendored/generated artifacts when identifiable

Do not count dependencies as part of the target project's own source statistics.

Metrics
-------
For each crate/configuration collect at least:

SOURCE SIZE
- production Rust files
- physical LOC
- nonblank LOC

FUNCTION-LEVEL
- total functions/methods
- safe functions/methods
- unsafe functions/methods
- functions/methods containing one or more unsafe blocks
- percentage of functions/methods containing no explicit unsafe

UNSAFE STRUCTURE
- unsafe fn count
- unsafe trait count
- unsafe impl count
- unsafe block/expression count
- estimated LOC inside explicit unsafe blocks
- percentage of production LOC inside explicit unsafe

CONCENTRATION
- files containing unsafe
- percentage of files containing unsafe
- unsafe counts per file
- top 10 unsafe-heavy files
- fraction of all unsafe blocks/LOC contained in top 5 files

Store raw counts. Do not only store percentages.

External scanners
-----------------
Integrate existing tools where practical instead of pretending our parser is a formal Rust analyzer.

Preferred:
1. cargo-geiger
2. count-unsafe

Detect whether each tool is installed.

If unavailable:
- report TOOL_UNAVAILABLE clearly
- continue collecting metrics that our own scanner can safely collect
- never fabricate equivalent results

If these tools expose machine-readable output, capture and preserve it.

Do not parse human-readable output with fragile regex if a stable JSON/machine-readable mode exists.

Our scanner
-----------
Implement a local Rust source scanner for metrics not conveniently exposed by external tools, especially:
- LOC
- file counts
- unsafe concentration
- approximate unsafe-region LOC

Avoid naive substring counting such as searching for the text "unsafe".

Prefer a real Rust parser if a lightweight reliable Python-accessible option exists. If that would add an unreasonable dependency, implement a conservative lexical scanner that:
- ignores comments
- ignores string literals
- recognizes unsafe fn
- unsafe trait
- unsafe impl
- unsafe { ... }
- correctly matches nested braces well enough for LOC-span measurement

Clearly label locally-derived unsafe LOC as an estimate.

Add something like:

Do not invent commit hashes.

If commits have not yet been chosen, support exact Cargo versions or leave an explicit field requiring the user to pin them before a real run.

Fail validation if an experiment is unpinned.

Execution
---------
Add a CLI consistent with the existing project style.

Desired interface:

python -m rust_baseline.cli validate-config \
    --config configs/rust-baseline.toml

python -m rust_baseline.cli scan \
    --config configs/rust-baseline.toml \
    --crate redb \
    --mode default

python -m rust_baseline.cli scan \
    --config configs/rust-baseline.toml \
    --crate redb \
    --mode all-features

python -m rust_baseline.cli scan-all \
    --config configs/rust-baseline.toml \
    --mode default

python -m rust_baseline.cli report \
    --results results/rust-baseline/<experiment-id>

Modes:
- default
- all-features

Use isolated checkout/worktree/cache directories so the user's existing repositories are never modified.

Never run destructive git operations against an existing checkout.

Build awareness
---------------
cargo-geiger can depend on what actually compiles.

Record separately:
- source-level unsafe measurements
- build-aware cargo-geiger measurements

Do not silently merge them into one metric.

If a crate fails to build:
- preserve source-level results
- record build/scanner failure
- save stdout/stderr
- continue other crates when scan-all is used

Example columns:

Do NOT automatically write prose such as:
- "Rust projects are generally 99% safe"
- "80% is a good threshold"
- "RustyCpp should achieve X%"

That interpretation belongs outside this tool.

- raw_pointer

- other

Do NOT implement unreliable automatic semantic classification in v1 unless there is a clearly defensible method.

For v1 it is acceptable to emit an empty/manual classification field.

5. Preserve raw scanner outputs.

10. Favor correctness of measurements over adding more metrics.
