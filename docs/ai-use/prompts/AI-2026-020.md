## Exact human-authored prompt

Manually audit libzmq and several possible replacement targets for RustyCpp migration feasibility.

Do NOT rely solely on the existing Rusty-eval inventory classifier. You may use its output as a secondary reference, but the main judgment must come from reading the actual source code, build structure, APIs, and representative implementation files.

Targets:
1. libzmq
2. Apache Thrift C++
3. eCAL
4. Boost.Beast
5. POCO Net
6. C++ Actor Framework (CAF)

Goal:
Determine which projects are realistic candidates for achieving >80% safe RustyCpp migration by production function count while still being meaningful infrastructure projects.

For each target:

1. Identify a reasonable production scope.
   - Exclude tests, examples, benchmarks, generated code, vendored dependencies.
   - Do not cherry-pick only easy directories.
   - If the whole repository is too broad, identify a coherent core library/module and explain the scope.

2. Manually inspect representative source files.
   Include:
   - several large implementation files
   - core public/internal classes
   - ownership-heavy code
   - networking/I/O code
   - callbacks
   - concurrency/threading
   - raw pointers
   - templates/virtual interfaces
   - external library/OS boundaries

3. Sample at least ~30–50 production functions per project if feasible, spread across different files/subsystems.

4. Classify manually inspected functions as:

A — DIRECT SAFE MIGRATION
Ordinary logic that appears expressible in RustyCpp DSL without significant redesign.

B — LOCAL REFACTOR
Likely safe-migratable, but needs localized ownership/lifetime/interface restructuring.

C — BOUNDARY
Should probably remain at a narrow C++/unsafe boundary:
OS APIs, sockets, threading primitives, FFI, external runtimes, allocator internals, raw callback ABI, etc.

D — HARD / CURRENTLY UNSUPPORTED
Would require major architectural changes or appears incompatible with current RustyCpp capabilities.

5. Pay special attention to whether difficult code is CONCENTRATED or SCATTERED.

A project where 15% of functions are difficult but concentrated in a few boundary files is more attractive than one where unsafe/runtime concerns appear throughout the codebase.

6. Give a MANUAL feasibility estimate:

direct_safe_pct ≈ A / sampled production functions

safe_with_local_refactor_pct ≈ (A+B) / sampled production functions

These are estimates, not measured migration results.

Do not manipulate classifications to get above 80%.

7. Compare the manual audit against any existing Rusty-eval inventory result.

For each project report:

inventory estimate
manual estimate
whether they broadly agree
major reason for disagreement

If the inventory says 90% but manual inspection suggests 70%, explain why.

8. Specifically investigate libzmq.

Determine why its current inventory estimate is only about:

70.4% direct
71.0% with refactor

Identify the dominant sources of difficulty and whether they are intrinsic to libzmq's architecture or artifacts of the evaluator.

9. Rank the candidates for this study using:

- infrastructure relevance
- similarity to libzmq / messaging-networking use case
- likelihood of >80% safe migration
- manageability
- size/complexity
- diversity relative to Raft, LevelDB, FlatBuffers, and Masstree

Output a concise table:

Project
Scope
Functions manually inspected

A+B %
Boundary/hard %
Difficulty concentration
Infrastructure relevance
Manageability
Recommended? yes/no

Then give a final ranking from strongest to weakest candidate.

Important:
- Actual source inspection is the primary evidence.
- Do not just run Rusty-eval and repeat its classifications.
- Do not equate "no obvious raw pointer" with safe-migratable.
- Consider cross-function ownership, lifetimes, callbacks, templates, virtual APIs, concurrency, and cross-TU interfaces.
- Do not modify any target repository.
- Do not perform migrations.
- Do not write research conclusions.
- Clearly label all percentages as manual feasibility estimates.
